# 山海足迹世界视图规格

> **状态：待实现。** 本文是规格，描述要做什么以及为什么这样做，**不描述当前行为**：仓库里目前没有世界地图、世界数据、世界接口或任何相关配置，用户可见行为仍以 [功能描述](features.md) 和 [数据与地图说明](data-and-maps.md) 为准。实现完成后，当前行为写入这两份文档，本文只保留决策记录。
>
> 需求与已确认范围：[kongken/mono#97](https://github.com/kongken/mono/issues/97)。本文把它落成可实施的约束，并给出各子任务共用的决定；实施拆分见本文第 12 节。
>
> 文中区分“已确认范围”（来自 #97，不可悄悄改变）与“工程决定”（本文补齐，实现前可评审调整，但必须同步修改本文与验收）。所有字段名、存储键、接口名都是拟定，不是当前可用能力。

## 1. 目标与范围

在山海足迹里新增**世界视图**：国家/地区级着色，加海外城市点位。保留现有中国省市足迹，不建设全球城市行政边界。

### 已确认范围（来自 #97）

- 中国/世界切换；中国功能、34 省 / 497 区域 / 391 目的地统计及旧备份不变。
- 世界边界静态分发、离线可绘制，无第三方地图请求或 Key；中文国家/地区目录可搜索，小区域通过列表进入。
- 国家/地区独立标记与海外城市分别保存；去过任一城市自动点亮所属国家/地区；取消独立标记不删城市。
- 中国现有足迹自动点亮世界上的中国；港澳台在世界视图统一归中国，现有国内记录和 ID 不变。
- 海外城市由用户命名并在地图选点（WGS-84），不把国家中心冒充城市坐标；可记录多次旅行、日期、备注。
- 世界统计单列，不改变中国统计与成就。
- 本机持久化、世界 JSON 备份；账号云端保存按用户隔离，离线待同步，多端版本冲突显式选择，禁止静默覆盖。
- 地图边界来源、授权、争议边界和覆盖限制明确展示。

### 第一版不包含

- 全球城市行政边界、第三方地理编码、海外照片/共同旅行/行程规划。
- 中国年度报告、成就和公开分享扩展到世界；世界备份单独导入导出。
- 工程决定：世界数据同样**不进入**云端快照（F3）、搜索（F9）、分享与预览图（F6）、好友与共同旅行（F7）、行程（F11）、提醒（F12）和媒体（F4）。这些功能的行为与现在逐字相同。

## 3. 国家/地区目录与 ID

- **ID**：ISO 3166-1 alpha-2 两位大写字母，如 `JP`。ID 一经发布不改号、不重用；目录变更须在规格中另行登记迁移规则，第一版没有迁移机制，未知 ID 一律拒绝（进入读取失败保护，不猜测、不清空）。
- **目录条目的取舍规则**（按顺序，前者优先）：
  1. 来源数据里有 ISO 3166-1 码的实体，保留各自的码，**即使存在领土或承认争议**（如 `EH`、`PS`）；唯一的例外是 `HK`、`MO`、`TW`，它们并入 `CN`，不单列；
  2. ISO 之外只增加 `XK`（科索沃）；
  3. 来源数据里没有 ISO 码的实体（如北塞浦路斯、索马里兰）并入其通行的主权国家 ID（`CY`、`SO`），不新增非 ISO 码；
  4. 每一项归并和例外由数据任务逐项列入文档，并随边界说明展示。
- **港澳台并入中国**：世界视图统一归 `CN`。目录里没有 `HK`、`MO`、`TW` 条目，地图上也没有独立几何；这只是世界视图的归并，不修改任何国内区域 ID、`regions.json`、旧备份和中国统计。
- **目录内容**：每项含 `code`、中文名、英文名、别名、所属大洲、是否有可点击多边形（`hasShape`）、地图标签用的代表点。代表点**只用于标注，不得作为任何海外城市的坐标或默认值**。目录由生成脚本从来源数据产出并带内容摘要（仿 F10 的区域目录），前后端各持有逐字一致的副本，检查脚本负责一致性。
- **小区域**：没有多边形或在世界视图下过小的国家/地区，仍在目录中，**目录列表是保证可达的入口**：搜索、标记、取消标记、作为海外城市的所属国家都不依赖点击地图。
- **搜索**：中文名、拼音、英文名、别名、ISO 码均可命中（如“日本”“riben”“Japan”“JP”）。

## 4. 数据模型 v1

本机存储、JSON 备份和云端文档使用同一结构：

```json
{
  "kind": "world",
  "version": 1,
  "countries": [
    { "code": "JP", "color": "#719fc6" }
  ],
  "places": [
    {
      "id": "p0mgx3k1y8c4f2a9z",
      "name": "东京",
      "country": "JP",
      "lat": 35.6762,
      "lng": 139.6503,
      "trips": [
        { "id": "t0mgx3k2a1b3c4d5e", "date": "2026-04-01", "note": "樱花季" },
        { "id": "t0mgx3k2z9y8x7w6v", "date": "", "note": "" }
      ]
    }
  ]
}
```

| 字段 | 含义与约定 |
| --- | --- |
| `kind` | 必填，固定为 `"world"`。用来让世界备份与中国备份互相识别并互相拒绝：中国备份没有 `kind`，也没有 `countries` / `places` |
| `version` | 数据结构版本，第一版只接受 `1`；其他值（包括更高版本）进入读取失败保护，不按空数据覆盖 |
| `countries` | **国家/地区独立标记**数组，每个 `code` 唯一；不得含 `CN`（见第 5 节）。只保存用户明确点击的标记，不保存因海外城市或中国足迹而派生的点亮 |
| `countries[].code` | 目录中存在的国家/地区 ID，且不是 `CN` |
| `countries[].color` | 五种足迹色之一（与中国足迹相同的调色板，见 [数据与地图说明](data-and-maps.md)） |
| `places` | 海外城市数组，每个 `id` 在城市之间唯一 |
| `places[].id` | 稳定 ID，匹配 `^[A-Za-z0-9_-]{1,64}$`；新城市为 `p` 加 9 位时间（base36）与 8 位随机字符 |
| `places[].name` | 用户命名，去首尾空白后 1–60 个 UTF-16 码元；不含 Unicode `Cc` 类控制字符（U+0000–U+001F、U+007F–U+009F）和孤立代理项；不做 Unicode 归一化，除去首尾空白外按输入原样保存；允许同名城市（以 ID 区分）。保存与返回的是去掉首尾空白后的值：本机读取、导入和云端写入遇到首尾带空白的名称时，一律裁剪后接受，不当作错误（裁剪后为空才拒绝）。“空白”的精确集合见下文“规范形式” |
| `places[].country` | 所属国家/地区 ID，目录中存在，且**不是 `CN`**（国内城市使用中国视图） |
| `places[].lat` / `lng` | WGS-84 十进制度，`lat ∈ [-90, 90]`、`lng ∈ [-180, 180]`，有限数字，**最多 6 位小数**。界面在写入前把任意输入规范到 6 位（四舍五入，远离零取整）；读取与导入遇到超过 6 位小数的值一律拒绝，不静默改写；检测方法是 `|x × 10^6 − round(x × 10^6)| < 1e-6` 视为规范（对 `|x| ≤ 180`，浮点误差远小于该阈值），边界样例（含恰在阈值上的 `1e-12` 与略低于阈值的 `9.9e-13`）列入共享夹具。云端接口以整数微度（`lat_e6` / `lng_e6`，`round(x × 10^6)`）传输，服务端没有浮点比较，所以不存在这一检测 |
| `places[].trips` | 该城市的旅行数组，可以为空（城市点位保留）；每次旅行的 `id` 在**整个文件内**（所有城市的旅行之间）唯一。城市 ID 与旅行 ID 是两个互相独立的编号空间：一个城市 ID 可以与某次旅行的 ID 相同，不算重复 |
| `trips[].id` | 匹配 `^[A-Za-z0-9_-]{1,64}$`；新旅行为 `t` 加 9 位时间与 8 位随机字符 |
| `trips[].date` | `YYYY-MM-DD` 的真实日历日期，或空字符串；规则与 F5 完全相同，共用 `packages/fixtures/trip-dates.json`（前端、后端同时校验） |
| `trips[].note` | 备注，最多 1000 个 UTF-16 码元，与 F5 一致 |

**规范形式**：同样的数据只有一种规范形式，由下列规则唯一确定；前端（TypeScript）与后端（Go）按同一组夹具 `packages/fixtures/world-documents.json`（有效与无效文档，含空白、控制字符、孤立代理项、坐标边界与超过 6 位小数的样例，仿 `trip-dates.json`）验证一致；夹具里带 `scope` 的用例只适用于特定场合：`json-text` 依赖 JSON 文件的形状、类型、另一种备份类型的文件或浮点小数位（未定义字段、错误的 JSON 类型、中国备份、超过 6 位小数），云端接口传带类型的消息和整数微度，所以 Go 测试只在解码 JSON 文档时才运行它们，并且先判 `kind`、`version`，再判未知字段（与 TypeScript 校验器的顺序一致，否则严格解码会先报中国备份里的 `visits`）；`utf16` 需要孤立代理项，Go 的 JSON 读取器会把它换成 U+FFFD、protobuf 字符串也装不下，Go 测试跳过。没有 `scope` 的用例两端必须一致：

- `countries` 按 `code`、`places` 与 `trips` 按 `id` 升序；`code` 与 `id` 只含 ASCII 字符，按码点（字节）比较，UTF-16 与 UTF-8 的顺序一致。
- 字符串长度一律按 UTF-16 码元计（Go 端转换后计数），与 F5 的备注规则相同。
- 名称去首尾空白时去掉的字符集合是 Unicode `White_Space` 属性的全部字符加 U+FEFF，由夹具逐码点列出，两端不使用各自语言的默认 trim。
- 坐标的规范值是整数微度 `E6 = round(x × 10^6)`；界面输入的舍入规则见上表，已经规范的值与其 `E6` 一一对应。
- “完全相同”（用于同步时判断云端是否已等于待发送目标）是规范化后的**结构相等**，不是字节相等；请求摘要只由服务端计算（见第 9 节），客户端不计算摘要，所以不存在两端字节不一致的问题。

不保存记录级时间戳：版本冲突按整份文档处理，旅行日期也不充当修改时间。

**严格校验**：以下情形一律拒绝，前后端使用上述夹具验证：未知 `kind` / `version`、未知或重复的国家/地区码、`CN` 出现在 `countries` 或 `places[].country`、重复的城市或旅行 ID、不合法的 ID 字符、名称为空、超长或含控制字符/孤立代理项、坐标非有限数字、越界或超过 6 位小数、日期不是真实日历日期、备注超长、出现未定义字段（不静默丢弃）。

**上限**：城市最多 5000 个，全部旅行最多 10000 次，文档中**所有字符串字段（`id`、`name`、`country`、`code`、`color`、`date`、`note`）的 UTF-8 字节数之和**最多 2,500,000。这个度量在 TypeScript（`TextEncoder`）与 Go（`len`）里计算结果相同，不依赖任何序列化格式；它保证接口消息远小于仓库的网络上限（公网读取上限 `grpcx.LegitimatePayloadBytes` 为 16 MiB，内部消息上限为 20 MiB，见 `internal/platform/grpcx/grpcx.go`）。这是新数据结构，不存在需要无损读取的旧备份，所以不像 F5 那样回避上限；超限在本机编辑、导入和云端写入三处都**明确拒绝并提示**，不截断、不静默丢弃。导入文件大小另限 4,000,000 字节。

## 5. 点亮规则

国家/地区 `X` 在世界视图中点亮，当且仅当下列任一成立：

1. `countries` 里有 `X` 的独立标记；
2. 任一海外城市的 `country` 是 `X`；
3. `X` 是 `CN`，且**当前显示的中国足迹**至少有一条城市足迹或一个省份独立标记（港澳台的足迹同样算）。

要点：

- **`CN` 完全派生。** 它不写入世界数据，不能被独立标记或取消，海外城市也不能属于 `CN`。点击世界视图上的中国进入中国视图。
- “当前显示的中国足迹”：未登录时是本机 `shanhai-travel-v2` / `v1` 读出的足迹；登录后是该账号的云端足迹（含未同步修改）。世界视图只**只读**这份摘要，不写入、不改动中国数据。
- 中国本机足迹处于 F0 读取失败保护时，世界视图不点亮 `CN`，并提示“中国足迹暂不可读取”，不触发任何写入。
- **取消独立标记不删城市**，仍因城市点亮的国家/地区保持点亮；**删除城市**须二次确认，且同时删除其旅行，不影响任何独立标记；删除后若该国家/地区没有独立标记，也没有其他城市，则熄灭。
- **着色**：有独立标记的国家/地区用其标记色；仅因城市或中国足迹点亮的用固定山野绿 `#4b937d`。新标记的颜色沿用中国足迹的选色规则：在已有国家/地区独立标记里选使用次数最少的颜色，次数相同按调色板顺序，标记保存具体颜色值，之后不重算。

## 6. 统计口径

世界统计单列展示，不并入中国统计、年度报告、成就和分享：

| 指标 | 计算方式 |
| --- | --- |
| 国家/地区数 | 第 5 节点亮集合的元素个数；被点亮的中国计 1 |
| 海外城市数 | `places` 的条数 |
| 旅行次数 | 全部海外城市下的旅行总数；同一城市多次旅行只增加它 |

验收样例：未登录标记日本、添加东京点位并记录两次旅行，得到国家/地区 1、海外城市 1、旅行 2；此时没有中国足迹，所以中国不计入。

## 7. 本机存储与备份

| 键 | 内容 |
| --- | --- |
| `shanhai-world-v1` | 本机世界数据（第 4 节结构）。键名里的 `v1` 是存储位置的代际，与 `version` 字段无关 |
| `shanhai-world-v1-conflict-<时间戳>` | 多标签页竞争覆盖前另存的对方页面原文 |
| `shanhai-world-v1-unreadable-<时间戳>` | 读取失败保护中，用户选择恢复或以空数据开始之前复制的原文 |
| `shanhai-world-cloud-v1:<用户 UUID>` | 账号缓存，见第 9 节 |

**不读写** `shanhai-travel-v2` / `v1`、`shanhai-cloud-v2:<用户 UUID>` 及其他中国相关键；中国备份格式保持 `version: 2` 不变，导出与升级前逐字一致。

读取失败保护、写入失败、多标签页竞争沿用 F0 的规则（见 [数据与地图说明](data-and-maps.md) 的“本地存储与兼容性”）：

- 启动时读取并校验，只在用户编辑、导入或处理保护窗口后才写入完整数据，仅打开页面不改写。
- 写入前检查存储文本仍是本页上次读取或写入的版本，否则暂停并交给用户选择；覆盖前把对方页面的原文另存为 `-conflict-<时间戳>`，保存失败时必须先导出同一份原文。
- JSON 无法解析、校验失败或 `version` 未知：保留原始字符串、暂停自动保存，用户可导出原文、恢复可识别的记录或以空数据开始；后两者先复制原文到 `-unreadable-<时间戳>`。例外：`version` 未知（含更高版本）时不提供“恢复可识别的记录”，只能导出原文或以空数据开始，因为用当前版本的规则有损地解读另一版本的数据会丢失内容；这与中国足迹对未知版本的做法一致（只恢复 `version` 为 1 或 2 的数据）。恢复只保留通过校验的记录并统计丢弃数，不修补；保留下来的记录仍超过上限时不截断，视为不可恢复；文本里的记录总数（标记、城市、行程）超过 30,000（约为合法上限的两倍）时不扫描、不提供恢复，原文照常保留，仍可导出原文或以空数据开始。缓存不存在或为空是正常首次使用。
- 写入失败（存储不可用或已满）：本机模式与 F0 一致，显示保存异常提示，内存中的数据仍可导出，不覆盖存储里已有的内容；页面关闭后不保证保留未写入的数据。账号模式更严格：账号缓存写入失败时拒绝本次编辑并提示导出（见第 9.2 节）。
- 这些副本不会自动清理，也不会被应用读取。

**JSON 备份**：导出为单独的世界备份文件（文件名前缀区别于中国备份），内容即第 4 节规范形式的文档；导入先校验再显示预览（新增 / 覆盖 / 丢弃的数量），确认前不写入存储。本机模式的导入是**整体替换**本机世界数据，确认前提供当前数据导出。中国备份与世界备份互相拒绝并说明原因，不静默丢弃。

## 8. 登录模式

- 登录后，世界视图只显示并编辑**该账号的云端世界文档**。登录前保存在本机的世界数据不显示，也**不自动上传**；退出登录后回到本机世界数据。账号弹窗若发现本机有世界数据，仅提示“可导出后在账号模式导入”。
- 账号与未登录数据、账号 A 与账号 B 的世界数据互不读写。账号切换沿用既有规则：`Me` 返回的用户 UUID 变化时切换到对应缓存，原账号的未同步内容原样保留。
- 账号模式下允许导入世界 JSON，语义是**整体替换云端文档**：必须先预览、确认，并在确认前提供当前账号文档的导出；它走与普通编辑相同的缓存与 `revision` 并发流程。
- 导出始终可用，导出的是当前账号在页面上的世界数据（含未同步修改）。
- 注销账号会删除该用户的世界文档，并清除该账号的世界缓存键（含 `-conflict-` 副本）；其他账号的缓存保留。

## 9. 云端模型

整体方案不变：每用户一份世界文档，整体替换，冲突由用户整体选择；**不做逐记录合并**。本节把并发、幂等和客户端状态机写成可直接实现的规则。

### 9.1 存储与接口（拟定）

每个用户至多一份世界文档，附单调的 `revision`。服务端新增 `WorldService`（浏览器契约 `bff.tripmap.v1`，内部契约 `tripmap.v1`，BFF 适配 `internal/bff/tripmap/world/`）。文档按第 4 节的结构用类型化 protobuf 消息表示（坐标为 `lat_e6` / `lng_e6`），不是 JSON 字符串。

- `GetWorld`：返回 `revision` 与文档；新用户返回空文档（`countries` 与 `places` 为空）和 `revision = 0`。
- `ReplaceWorld`：请求带 `base_revision`、持久化的 `request_id`（匹配 `^[A-Za-z0-9_-]{1,64}$`）和完整文档。响应带 `applied`（是否生效）、`replayed`（是否为回执重放）、`revision`、`document` 和 `cloud_revision`（服务端当前的最新版本）。

**服务端判定顺序**（必须按此顺序，每一步在同一个数据库事务内完成）：

1. **格式与文档校验**：`request_id` 格式、第 4 节的全部校验与上限。失败返回 `INVALID_ARGUMENT`，不改动任何状态，也不记回执。
2. **回执重放（先于 `base_revision` 判定）**：在该用户的回执里查找 `request_id`。
   - 找到且请求摘要相同：原样返回当时的结果，`applied = true`、`replayed = true`、`revision` 为回执里的结果版本、`document` 为该请求自带的文档（摘要相同，所以与当时存入的完全一致），`cloud_revision` 为当前最新版本；不递增 `revision`，也不再检查 `base_revision`。
   - 找到但摘要不同：返回 `ALREADY_EXISTS`（同一 `request_id` 被用于不同内容），不改动任何状态。
3. **比较并替换**：在行锁（或等价的乐观比较）下读取当前 `revision`。
   - `base_revision` 等于当前 `revision`：内容与云端相同则不改动、不加 `revision`；否则写入并把 `revision` 加 1。响应 `applied = true`、`replayed = false`、`revision` 与 `document` 为写入后的状态；并**为这次请求记一份回执**（含内容未变的空操作）。
   - `base_revision` 不等于当前 `revision`：不改动云端，不记回执；响应 `applied = false`，`revision` 与 `cloud_revision` 为云端当前版本，`document` 为云端当前文档。这是冲突，不是错误。

**并发要求**：同一 `base_revision` 的并发请求只能有一个成功，其余按冲突返回；新用户首次写入的并发创建依赖“每用户唯一”的数据库约束，失败方重新读取后按冲突返回，不得返回内部错误。

**回执**：每个用户保留最近 32 份成功请求的回执（`request_id`、请求摘要、结果 `revision`），超出时删除最旧的。摘要是服务端对 `base_revision` 与第 4 节规范形式的校验后文档两项计算的 SHA-256（字段顺序与编码由服务端固定，客户端不参与），所以同一 `request_id`、同一文档但不同 `base_revision` 不算重放，按 `ALREADY_EXISTS` 处理。回执只保存摘要，不保存文档。
- 丢响应后客户端用同一 `request_id` 重放，只要期间没有超过 32 次其他成功写入，就得到 `applied = true`，即使其他设备已在中间写入新版本。客户端按 `revision` 小于 `cloud_revision` 的情况继续同步（见 9.2）。
- 回执已被淘汰时，重放按第 3 步处理，得到冲突；若云端文档恰好等于待发送目标，客户端静默视为成功，否则进入冲突窗口。这是有意的安全降级：只会多问一次用户，不会重复写入，也不会丢数据。

**其他要求**：
- 所有读写以会话用户为准；写入沿用现有的 CSRF、`X-Kongken-User` 账号守卫，以及产品应用已登记的 Origin/CORS 检查（与足迹接口相同），不增加任何绕过。需要在 `internal/bff/gateway/services.go` 登记路径，携带凭据的路径填写 `Trace`。
- 世界文档与回执是两个新的 Ent 实体（拟定为 `world_documents`、`world_receipts`），都在 `internal/tripmap/accountcleanup` 里登记（其 `registry_test.go` 要求每个实体显式登记），迁移放在 `migrations/tripmap/`，不改动既有表。

### 9.2 客户端同步

沿用 F1 的“先写本机、再发送”保护，但同一时刻只有一个在途请求，不做逐记录三方合并。

**账号缓存** `shanhai-world-cloud-v1:<用户 UUID>` 保存 `{schema:1, saved, confirmed, pending?}`：

- `confirmed`：`{revision, document}`，最后一次被云端确认的状态。
- `saved`：页面当前的目标文档（包含所有编辑）。
- `pending`：`{request_id, base_revision, document}`，**已生成的唯一在途请求**。生成后不可修改。
- 缓存无法解析或校验失败时保留原文、阻止覆盖、提供导出原始缓存。

**规则**：

1. **编辑**：先把新的 `saved` 写入缓存，写入失败则拒绝这次编辑并提示导出。随后，若没有 `pending` 且 `saved` 与 `confirmed.document` 不同，就生成 `pending`（新的 `request_id`，`base_revision = confirmed.revision`，`document` 为当前 `saved` 的快照），先写入缓存，再发送。若已有 `pending`，**只更新 `saved`，不改 `pending`**（改了会触发 `ALREADY_EXISTS`，换新 ID 又会和自己刚生效的请求冲突）。
2. **确认**：收到 `applied = true`（含重放）：`confirmed = {revision, document}`（取响应里的值），清除 `pending`；若 `saved` 仍与 `confirmed.document` 不同，立即按规则 1 生成下一个 `pending`，其 `base_revision` 为刚确认的 `revision`。如果 `cloud_revision` 大于响应的 `revision`，说明其他设备已写入更新版本：此时若 `saved` 仍与 `confirmed.document` 不同，下一个请求会按规则 4 走冲突路径，这是真实冲突；若没有后续本地差异，立即按规则 7 调用 `GetWorld` 并无提示地采用云端，不等到下次启动、可见或联网。
3. **失败与离线**：网络失败、超时或丢响应不回滚也不丢弃修改，显示“本机已保存，待同步”；联网、页面重新可见或点击重试时用**原** `pending`（相同的 `request_id` 与内容）重放。离线修改跨刷新保留。
4. **冲突**（`applied = false`）：先比较云端文档与 `pending.document`、`saved`（结构相等）。等于 `pending.document` 或等于 `saved`：视为已成功，`confirmed` 取云端的值，清除 `pending`，不打扰用户（`saved` 若仍有差异则按规则 1 生成下一个请求）。都不相等：暂停写入，弹出冲突窗口。
5. **冲突窗口**：说明云端已被其他设备修改，提供“导出本机世界备份”和“导出云端世界备份”，再让用户选择，两个选项都先写缓存再发送：
   - **以本机为准**：`confirmed` 取云端最新的 `{revision, document}`，生成新的 `pending`（**新的** `request_id`，`document` 为当前 `saved`，`base_revision` 为云端 `revision`）；这次请求若再次冲突，再次弹出窗口。
   - **以云端为准**：`saved` 与 `confirmed` 都取云端值，清除 `pending`，本机未同步的修改丢弃。
   不提供自动合并，**绝不静默覆盖**。窗口出现期间编辑被暂停。
6. **`ALREADY_EXISTS`**：属于客户端缺陷，不是用户冲突。丢弃当前 `pending` 的 `request_id`，沿用原 `pending` 的 `document` 与 `base_revision`、换新的 `request_id` 重新生成 `pending`，不是用最新的 `saved`（若原请求其实已生效，则按规则 4 的“云端等于目标”静默成功；之后 `saved` 的差异再按规则 1 生成下一个请求）。
7. **启动、页面可见、联网**：若有 `pending`，按规则 3 重放。没有 `pending` 且 `saved` 等于 `confirmed.document`：调用 `GetWorld`，云端 `revision` 更高时无提示地采用云端（`saved = confirmed = 云端值`）。
8. **没有缓存**：登录后首次进入世界视图且没有账号缓存时必须先成功 `GetWorld`；拉取失败（含离线）时世界视图显示“无法加载云端世界足迹”和重试，**不接受编辑**，中国视图不受影响；会话失效时给出前往 OzID 重新登录（与 F1 的“启动与离线”一致）。有缓存时离线仍可编辑并跨刷新保留。
9. **多标签页**：账号缓存写入前同样检查存储文本仍是本页上次读写的版本，不一致则暂停本标签页编辑，提示“其他标签页已修改，请重新载入”，把对方原文另存为 `shanhai-world-cloud-v1-conflict:<用户 UUID>-<时间戳>`，不覆盖。发送互斥优先使用 Web Locks（`shanhai-world-sync:<用户 UUID>`）；不可用时允许两个标签页发送同一个 `pending`——它们读的是同一份缓存里的同一个 `request_id`，由服务端回执保证幂等。
10. **账号切换与 CSRF**：账号切换保护、`X-Kongken-User` 头、CSRF 令牌被其他页面替换时的一次重放，复用现有机制，不改变其行为。

选择整体替换而不是逐记录合并的理由：世界数据体量小、结构简单，#97 明确要求冲突“显式选择”并允许“先导出再选择”；逐记录合并需要记录级时间戳、删除标记和增量日志，会显著放大后端与前端范围。如果评审要求逐记录合并，须在本节改写，并相应调大后端与云同步阶段。

## 10. 地图数据与展示

- **基准与来源**：
  - **`CN` 的基准**是现有文件 `apps/trip-map/public/maps/100000.json`，由 34 个省级区域要素（含 `710000` 台湾、`810000` 香港、`820000` 澳门）和一个无名称的海上线要素 `100000_JD`（10 个部分，坐标已是真实经纬度，现有中国视图只是把它画在附图里）组成。世界视图**直接使用这份文件**绘制 `CN`，不复制、不简化、不修改它，所以 `CN` 的轮廓与现有全国地图在构造上一致，不需要容差校验。
  - **其他国家/地区**来自随项目分发的静态来源，其授权必须允许再分发和修改（简化、归并）；授权文本、来源、版本、输入文件的 SHA-256、改动说明保存在仓库并在界面展示。候选是 Natural Earth 的国家/地区数据（公有领域），以实际授权文本为准。运行时没有第三方地图请求，也没有 Key；世界视图不使用 OSM 或 Mapbox 底图。
- **`CN` 的绘制**：34 个省级要素以同一填充样式绘制，不画省界（可用同色细描边消除抗锯齿缝），在世界视图里合起来就是一个可点击的 `CN`；`100000_JD` 在其真实位置画成细线，不参与点击与点亮，**不使用附图**。
- **邻接边界规则**：来源数据中的 `CN`、`HK`、`MO`、`TW` 要素一律丢弃；其余国家/地区的多边形**不被裁剪、不被修改**；`CN` 在所有国家/地区之后绘制，覆盖与其重叠的邻国部分；来源与基准之间可能出现的缝隙或空洞不填补，并列入“覆盖限制”文案。点击与点选的命中判定同样按“`CN` 优先”：位置落在基准的任一省级区域内即判为 `CN`，其余位置才用来源多边形判定。
- **可复现与校验**（由 `npm run check:maps` 执行，不引入新依赖，只用现有的 `d3-geo`）：
  - 来源原始文件按固定的、带版本的 URL 下载（沿用 `download-maps.mjs` 的做法，不提交进仓库），其 URL、版本和 SHA-256 记录在目录元数据里；生成脚本（`prepare:world`）先校验输入的 SHA-256，不符则失败，再生成。
  - 生成脚本是确定性的：同一输入得到逐字节相同的输出。`check:maps` 离线运行，只校验已提交输出的摘要与目录元数据一致；确定性重生成需要网络，不放进 `check:maps`，而是由数据阶段的实施者连续运行两次 `prepare:world` 比对，并把结果与输入 SHA-256 写入 PR 说明。
  - 目录与几何一一对应：目录中 `hasShape` 为真的条目（`CN` 除外）与来源几何的 ID 集合相等；目录里没有 `HK`、`MO`、`TW`，几何里也没有它们的独立要素。
  - 世界视图加载的 `CN` 要素集合与 `packages/geo-data/data/regions.json` 的 34 个省级区域 ID 完全一致，且 `100000_JD` 的 10 个部分齐全；`100000.json` 的既有断言（省级要素数量、环绕方向、邻接表）保持通过。
  - 在 PR 说明里用固定步长的栅格法（0.25°，`geoContains`，按纬度余弦加权）给出“来源邻国与基准 `CN` 的重叠面积和空洞面积”，仅作信息记录，不是门槛，用于评审时判断覆盖限制文案是否准确。
- **体积预算**：新增的世界资源（非 `CN` 的边界、目录与搜索索引）gzip 后合计 ≤ 600 KB。复用的 `100000.json`（gzip 约 200 KB）不计入新增预算，但不得被修改，并且世界视图与中国视图共用同一个资源地址，由同一份缓存提供。超出预算须在数据阶段说明并重新评审，不能悄悄放宽。
- **争议边界与覆盖限制**：世界视图常驻“地图来源与限制”入口，展示来源、授权、边界依数据源绘制、可能与任何国家官方地图不同、地图仅用于个人旅行记录且不代表对任何领土主权的立场，以及小区域只能通过列表选择。具体文案由数据阶段写成常量供界面引用。
- **缩放与平移**：选点需要足够精度，世界地图必须支持缩放和平移（滚轮/双指、按钮、键盘），否则不能作为选点方式。
- **离线**：世界地图与目录断网后仍可绘制。原有 Service Worker 只处理推送、不缓存任何静态资源，所以由界面阶段（W3）新增：地图数据缓存按目录 `version` 区分名字、每次使用前校验 SHA-256（升级后旧缓存不被读取，不匹配的文件被丢弃），页面外壳缓存只在网络失败时由 `sw.js` 使用；实现与限制见 [数据与地图说明](data-and-maps.md)“世界视图的离线缓存”。
- **相机**：世界投影独立于现有 `lib/projection.ts` 的中国相机，不改变中国视图。

### 选点与所属国家

- 用户在地图上点击选点得到 WGS-84 坐标，同时提供经纬度输入作为键盘与无障碍的等价方式。名称由用户输入，没有第三方地理编码，也不从国家代表点取值。
- 所属国家/地区默认由点选位置所在的多边形建议，用户可在目录里改选；落在无多边形的小区域或海上时必须从目录选择；点选位置与所选国家/地区不一致时提示但允许（简化边界有误差，以用户选择为准）。
- 点选位置落在 `CN` 范围内（命中规则见上文“邻接边界规则”），或用户选择 `CN` 时，提示改用中国视图，不创建海外城市。

## 11. 界面与交互约定

- 页眉提供“中国 / 世界”切换，可键盘操作；打开页面总是中国视图（保持现有行为），切换不改写任何中国数据，也不记忆视图偏好。
- 中国视图的功能、统计、备份与升级前一致；世界统计面板单列，不并入中国统计、年度报告与成就。
- 键盘：
  - 有多边形的国家/地区在地图上必须可聚焦（有可访问名称和当前状态），Enter 或空格切换独立标记；`CN` 的 Enter 切换到中国视图。列表是另一条入口，**不能替代**地图上的键盘操作，与中国地图的区域聚焦保持一致。
  - 地图缩放和平移可用键盘（按钮、方向键、`+` / `-`）。
  - 搜索、编辑、删除确认都可键盘操作；选点的键盘方式是经纬度输入，地图上的点选以鼠标和触摸为主，第一版不要求十字准线式的键盘选点。
  - 焦点可见；桌面与 390px 手机下页面无横向溢出。
- 用户文案使用中文旅行手账风格，沿用现有浅色、绿色主题与 `@kongken/ui` 组件。
