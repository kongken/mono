# 后端功能调研

> 状态：调研与待实现。本文列出的功能、数据模型和接口均为**草案**，尚未实现，不属于当前应用行为。当前已实现的功能见 [功能描述](features.md)，数据约定见 [数据与地图说明](data-and-maps.md)。

后端技术选型与基础设施初始化已完成，见 [后端初始化](../backend.md)；以下业务功能仍为待实现草案。

## 目的与范围

山海足迹目前是纯浏览器本地应用：足迹保存在浏览器本地存储，通过手动导出、导入 JSON 备份，没有登录、云端同步、分享或附件能力。

本文用于后续后端开发，包含：

- 引入后端后可以实现哪些功能，以及各自的规则、依赖和验收场景。
- 数据模型、接口、同步和迁移的草案。
- 对现有约定的影响、隐私要求、技术选型倾向、分阶段交付和待决问题。

草案中的字段名、路径和规则不是最终约定。实现某项功能时，应在 [功能描述](features.md) 增加对应规则和验收场景；涉及数据字段、版本或备份校验时，同步更新 [数据与地图说明](data-and-maps.md)，并把本文对应条目改为“已实现”或删除。

## 现状与痛点

| 方面 | 当前实现 | 后端可以解决的问题 |
| --- | --- | --- |
| 存储 | 浏览器本地，按网站来源隔离 | 清除站点数据、更换浏览器或设备后记录丢失 |
| 备份 | 手动导出、导入，导入整体替换 | 忘记备份；误导入会覆盖现有记录；没有合并 |

## 功能详述

### F0 修复本地读取失败覆盖原数据（前置）

- **问题。** 启动时读取本地 JSON 失败或校验失败会回落为空数据，随后的自动保存可能覆盖原缓存。同步后还可能把空数据推到云端。
- > 状态：已实现（前端规划与预览，批量同步原子写入，无新增接口）；详细规则见 [功能描述](features.md) 的“本地足迹迁移”。

**当前规则。**

- 本地有数据且云端为空：提示后上传；本地与云端都有数据：只上传云端没有的，云端独有记录保留，同 ID 且内容不同的记录逐条选择，默认用云端，并提供“全部用云端 / 全部用本机”。
- 不按日期判定新旧，旅行日期不是修改时间；省份独立标记与城市足迹分别处理，同样逐条选择。
- 执行前预览新增、覆盖、保留、无需变动的数量，可导出云端备份；迁移不删除云端任何记录。
- 迁移是一个最多 2000 项的原子批次（F5 前为 600），不拆分：超过时预览阻止，不做快照也不发送。批次幂等重放，失败或断网保留在本机后重试，不会有半成品；“整体提交”的意图随账号缓存持久化（`atomic`），刷新、冲突、失败后仍然有效，迁移被接受后若总量又超限或缺少批量能力，已接受的内容与意图都保留、同步暂停，由用户导出或减少后再发，不自动回退。本机旅行 ID 与云端另一城市的旅行重复时上传使用新 ID。本机副本保留并以指纹记录“已迁移”。

**验收场景。** 见 [功能描述](features.md) “F2 迁移验收”四个场景。取消迁移时本地和云端都不变。

迁移前的自动云端快照已由 F3 实现（云端已有足迹时先保存，失败则不迁移）。**尚未实现。** 迁移本身没有单独的撤销入口（需通过迁移前快照恢复）。

### F3 云端备份与历史版本

> 状态：已实现（`SnapshotService`、前端“历史版本”窗口）；规则与验收场景见 [功能描述](features.md) 的“云端备份与历史版本（F3）”，接口与保留规则见 [后端初始化](../backend.md)。

**目标。** 误导入、误删除或被旧缓存覆盖时，可以恢复。

**当前规则。**

- 保存快照的时机：迁移前（云端已有足迹时）、恢复前自动保存；服务端每小时检查，账号有改动且 24 小时内没有快照时保存定时快照；用户也可手动保存。同一版本（revision）只保存一份。登录期间导入备份被禁用，因此没有“导入前”快照。
- 保留规则（默认值，尚待产品确认）：30 天，始终保留最新 10 个，每账号最多 50 个。
- 用户可以查看快照时间、来源与记录数量，预览恢复会找回、改写、移除多少记录，并选择恢复；恢复在服务端事务内完成，要求预览时的 revision 仍是当前版本，恢复前自动再保存一份当前快照，因此恢复可以撤销。
- 快照不可修改，账号删除时一并清除。

**验收场景。** 见 [功能描述](features.md) “F3 快照验收”七个场景。

**尚未实现 / 限制。** 快照不能手动删除或下载为备份文件；F10 支持已登记的一对一旧区域投影，未知版本/未映射/碰撞的快照仍无法预览或恢复；快照保留期限与数量未经产品确认；没有“批量清空类请求要求显式确认”的服务端接口。

### F4 照片与附件

**目标。** 足迹或旅行可以关联照片。

**规则草案（F4 当前实现见功能与后端文档）。**

- 限制类型（例如 JPEG、PNG、HEIC、WebP）、单文件大小和每条足迹的数量，具体数值待定。
- 上传由客户端直传存储，后端签发有时效的上传地址并登记元数据；读取使用有时效的访问地址或经鉴权的代理。
- 生成缩略图用于列表和地图卡片。
- 可选：读取 EXIF 拍摄地点建议所属城市，必须经用户确认后才写入；上传时默认剥离分享可见版本中的位置信息。
- 删除足迹或旅行时，关联照片按用户选择删除或保留。

**验收场景。** 上传照片后在足迹卡片看到缩略图；超限、非法类型被拒绝；删除后文件不再可访问；分享页默认不暴露照片，除非用户开启。

F4 已采用默认值：JPEG/PNG/WebP/PDF、10 MiB、20 个/城市；当前关联城市区域，取消打卡保留媒体，独立确认删除。不读取 EXIF 建议，照片重编码移除元数据；旅行子记录关联已由 F5 以可空软引用 `trip_id` 实现；HEIC 仍待后续实现。详细限制见 [功能描述](features.md) 与 [媒体接口](../backend.md#媒体接口f4tripmapv1mediaservice)。

### F5 同一城市多次旅行

**目标。** 一个城市可以有多次旅行，每次有自己的日期、备注和照片。

**状态：已实现**（见 [功能描述](features.md#同一城市多次旅行f5) 与 [后端升级与部署顺序](../backend.md#f5-升级与部署顺序)）。以下为已采用的规则；产品已确认：颜色规则不变，列表与最近足迹按城市最近一次有效旅行日期排序，删除最后一次旅行保留城市打卡，取消城市打卡删除其旅行（照片保留）。

**规则。**

- 城市足迹保留“区域 + 颜色”，旅行为其子记录（日期、备注、照片）。
- 现有记录迁移时，把原有日期和备注转成该城市的第一次旅行；空日期、空备注仍保留为一次旅行，避免丢失。
- 地图着色仍按城市足迹颜色，不随次数变化。
- 统计新增“旅行次数”；“已留下足迹”仍按城市数量，口径不变。
- 最近足迹和足迹列表按城市最近一次有效旅行日期排序，不展开为每次旅行。

**影响。** 已把“每个区域 ID 只保存一条足迹”改为“一条城市足迹下有多次旅行”，存储结构与备份格式升级到版本 2，并为旧备份、旧缓存与旧账号提供迁移。

**验收场景。** 同一城市添加两次不同日期的旅行，记录数量（城市）不变、旅行次数为 2；导入旧版本备份后，每个城市有一次旅行；删除其中一次旅行不删除城市足迹，删除最后一次旅行的行为待定。

### F6 公开分享页与分享海报

**目标。** 生成只读链接，展示省份探索度和足迹地图。

**状态：已实现**（见 [功能描述](features.md#公开分享页与预览图f6)、[公开分享页与预览图](sharing.md) 与 [后端 F6](../backend.md#f6-公开分享tripmapv1shareservice)）。按议题草案采用保守默认值（默认只含省份地图和统计，发布需显式确认）。

**已采用的规则。**

- 可见性：不公开（默认）、持有链接的人（noindex）、公开（可被收录，无目录）。
- 显式发布的快照：发布时保存内容，之后的足迹、备注和照片不自动公开；收回字段立即生效且不读取新足迹，新增或更新内容需预览并确认，预览后足迹变化则中止（`aborted`）。
- 可选字段：城市名称、日期、备注、照片（逐张选择自己的 JPEG，最多 12 张，无 PDF）。
- 链接撤销后链接、数据、照片和预览图立即统一 404；重新发布生成新令牌，令牌 256 位随机，不可猜测。所有对外响应 `no-store`，每次请求都校验令牌、可见性和账号状态。
- 服务端生成 1200×630 PNG 预览图（纯 Go、随项目分发的字体和几何），仅显示省份层级。公开响应是显式白名单，不含账号、旅行、媒体标识。

**当前限制（待实现或不做）。** 已被下载或平台缓存的内容无法收回；令牌明文存储；没有密码、过期、访问统计、目录；微信与微博不支持；Facebook、X、LinkedIn 等真实平台的抓取未验证；预览图不含城市名与照片。

**验收场景（已覆盖自动化）。** 开启分享后用无痕窗口访问可看到地图；撤销后返回不存在；备注和日期默认不出现；预览图能正确显示省份着色。

### F7 共同旅行与好友

**目标。** 邀请同行者共同记录同一次旅行，好友之间互看地图。

**状态：已实现**（见 [功能描述](features.md#共同旅行与好友f7)、[共同旅行与足迹归属](data-and-maps.md#共同旅行与足迹归属f7) 与 [后端 F7](../backend.md#f7-共同旅行与好友tripmapv1collaborationservice)）。

**已采用的规则。**

- 好友通过用户名或唯一邀请码（`fc_` 前缀）发起申请，需双方确认；可随时解除，解除后互相不可见，已加入的共同旅行解绑并保留为各自独立个人记录。
- 好友对比严格遵守双方各自的 `friend_show_cities/dates/notes` 设置（默认仅公开城市，不公开日期与备注）；仅当双方均开启“公开打卡城市”时才展示共同打卡城市对比。
- 共同旅行区分创建者（`owner`）、共同编辑（`editor`）和只读成员（`viewer`）；`owner` 与 `editor` 可共同编辑同一次旅行的日期、备注并上传照片，`viewer` 仅可查看，仅 `owner` 可管理成员角色、移除成员或解散共同旅行。
- 退出共同旅行仅移除该次共同旅行子记录，保留成员在该城市的打卡状态、原有颜色、其他个人旅行及个人媒体，且绝不误删他人记录。

**验收场景（已覆盖自动化）。** A 邀请 B，B 接受后双方在各自地图看到同一次旅行；共同编辑与上传照片同步可见；`viewer` 只读受限；B 退出后 A 的记录保留且 B 保留自己的城市打卡与其他旅行；解除好友后无法再查看对方地图。

### F8 统计、年度报告与成就

**状态：已实现**（见 [功能描述](features.md#足迹统计年度报告与成就f8) 与 [后端 F8](../backend.md#f8-统计年度报告与成就tripmapv1reportservice)）。

- 年度回顾：当年旅行次数、当年走过城市数、当年新增城市数量与首次打卡区域、跨越省份、最长旅行记忆与常去目的地。年度口径沿用现有统计口径（全国 391 城市合并直辖市与港澳，省内与区域明细按 497 个实际区域），旅行次数依赖 F5。
- 成就：8 项成就（初踏山海、十城足迹、半百风物、半壁山河、九州同游、全省制霸、故地重游、山海执笔人）规则已在文档中逐条列出，与统计口径完全一致，且每项年度统计与成就均可追溯并跳转到对应的省份、城市或旅行记录。
- 服务端按 `(user_id, revision, timezone, local_date)` 在 Redis 中缓存汇总结果，并由每小时维护任务定时预热；成就和报告按用户本地 IANA 时区计算当前日期与默认年份。
- 前后端共用 `packages/fixtures/report-stats.json` 测试夹具校验一致性；年度回顾提醒由 F12 发送（只含数量）。

### F9 搜索增强

**状态：已实现。** 规则与验收见 [功能描述](features.md#搜索与足迹查看)，接口、性能限制见 [后端 F9](../backend.md#f9-私有备注搜索tripmapv1searchservice)。

- 区域名称/简称、拼音、首字母及无直接匹配时的单次编辑纠错：前端离线静态索引，由 `packages/geo-data/data/regions.json` 生成，不增加地图请求或更改区域 ID，手机城市选择复用。
- `SearchService.SearchNotes`：仅当前用户范围内的完整备注字面片段 AND 检索（支持中文，无需中文分词扩展）；有界分页、revision 保护、限流与用户隔离，兼容旧账号；前端本地/离线/未同步时使用当前缓存，网络失败有明确提示与重试。
- 不新增数据库表、备注缓存或全文扩展；目前基于用户索引和参数化包含扫描，无 GIN/相关度排序、语义搜索或任意查询语法，超大数据集的专用搜索索引仍待后续测量。

### F10 行政区划数据服务（已实现）

- 内容摘要绑定静态区域索引和精确历史元组映射；前后端生成副本一致，服务端校验复用同一 Index。生产历史只包含金门/马祖实际归属变更，退休 ID 的一般机制由共享测试夹具验证，不伪造生产数据。
- 鉴权 `RegionService.GetRegionIndex` 条件按版本读取；`PreviewRegionUpgrade` 只读预览自己的变化/阻止项，`ApplyRegionUpgrade` 用户确认、revision 条件、用户行锁、迁移前快照、同步日志和幂等回执全部在一个事务中完成；旅行 ID、用户内容、媒体文件和独立省份标记保留。
- v1/v2 本地/账号缓存、备份、历史快照按已登记映射读取；首次覆盖旧缓存先保留原文，未知未来版本或目标碰撞暂停且保留数据；队列原请求不改，旧已提交回执仍能精确重放。区域版本不一致阻止新的同步写入。
- 地图 GeoJSON 仍静态分发，不在线更新边界；无新增数据库 schema。功能、字段和部署规则见 [功能描述](features.md#区域数据与兼容f10)、[数据与地图](data-and-maps.md#区域索引版本与维护f10)、[后端接口](../backend.md#f10-区域数据服务tripmapv1regionservice)。
- **限制：** 不抓取实时区划；不自动猜测未登记区域，不拆分或合并碰撞记录，不自动协调省份/共同旅行跨账号 ID 改号。未来真实 ID 改号与旧未发送批次并存时保留缓存、请求及修改，需先导出交由维护者处理；没有行政数据回滚入口。

### F11 路线规划与行程（已实现）

- 把多个城市连成一次行程，在地图上绘制路线。`ItineraryService`（列出/读取/保存/删除）全部鉴权并按用户隔离；保存带 `expected_version` 乐观并发和 `mutation_id` 幂等回执；账号注销级联删除；F10 区域迁移同时升级行程站点里的历史城市 ID。
- **估算供应方与规则：** 采用内置 `offline_great_circle`（城市中心点球面距离 + 交通方式系数与速度），保持“运行时无需第三方地图请求或 API Key”；费用为零；前后端用同一整数算法与共享夹具校验。后端对单段结果缓存在 Redis（`<prefix>:itinerary:leg:v1:<from>:<to>:<mode>`，24 小时），前端是确定性本地计算。若将来要接真实路线服务，须单独决定放宽该约定、费用和缓存，并保留此离线方案作兜底。
- 功能、字段和部署规则见 [功能描述](features.md#行程与路线连线f11)、[数据与地图](data-and-maps.md#行程与城市坐标f11)、[后端接口](../backend.md#f11-行程服务tripmapv1itineraryservice)。
- **限制：** 无实时路况/票价/班次、无步行骑行方案、无行程分享或共同编辑；估算仅供参考。

### F12 提醒与通知（已实现）

**状态：已实现（本地假 SMTP/假推送服务验证，未经真实邮件服务商与浏览器推送服务验证）。** 规则与验收见 [功能描述](features.md#提醒与通知f12)，配置、接口、表和部署见 [后端 F12](../backend.md#f12-提醒与通知tripmapv1notificationservice)。

- 回忆提醒（“一年前的今天”）与年度回顾提醒（1 月第一周，只含数量）；邮件（SMTP）与 Web Push（VAPID）两个渠道；每类、每渠道逐项开关，**默认全部关闭**；邮箱需 6 位验证码验证，退订使用签名链接（RFC 8058 一键退订）。
- 验收口径：提醒按用户时区和发送小时判断；关闭、退订、移除邮箱、注销后不再发送；通知不含备注和照片，默认不含地点，仅在用户勾选后才含城市名。
- 投递以 `notification_deliveries` 的唯一键（用户、类型、渠道、周期）保证同一周期至多发送一次；每小时一次的维护任务在 Redis 锁下运行，多实例不重复发送。
- **限制：** 没有站内收件箱、短信或 App 推送；投递语义是最多一次（崩溃时漏发而非重发），没有送达回执；每小时检查，实际发送最多晚约 1 小时；SMTP 与推送服务需要运营方自备并在生产环境单独验证。

## 同步设计草案

- **离线优先。** 本地缓存始终是读写入口，联网后后台同步。
- **版本号。** 服务端每个用户一个单调递增 `revision`；客户端记录已同步的 `revision`。
- **冲突。** 初期按记录粒度，以更新时间较新者为准，删除使用 `deleted_at` 标记并参与比较；后续可改为字段级合并。冲突结果在接口中返回，前端可提示用户。
- **幂等。** 同一变更重复提交不产生重复记录，可使用客户端生成的变更 ID。
- **防止空数据覆盖。** 客户端在本地读取失败（见 F0）时不得向云端推送；服务端对“批量清空”类请求要求显式确认，并先保存快照。
- **时间与时区。** 旅行日期是字符串日期，不随时区转换；`updated_at` 使用 UTC。

## 对现有约定的影响

| 现有约定 | 影响 | 建议 |
| --- | --- | --- |
| 区域 ID 一致，台湾使用 `tw-` 前缀 | 可直接作为后端区域标识 | 保持不变，作为外键或索引 |
| 省份独立标记与城市足迹分别存储 | 云端需保持同样的分离 | 同步时分别处理，删除一类不影响另一类 |
| 统计中已探索省份取两者并集 | 服务端统计需沿用同一口径 | 前后端共用同一份计算逻辑 |
| 存储结构版本为 `2`（F5 已升级，仍接受 `1`） | 后续改变结构时 | 升级版本号，提供迁移，不把旧数据当作空数据覆盖 |
| 地图随项目分发，运行时无第三方请求 | 后端不改变地图来源 | 保持静态分发；F11 使用内置离线估算，外部服务如需引入须单独决定 |
| 导入前提供确认和导出入口 | 迁移上云时需要保持同样的保护 | 合并、覆盖、恢复前都提示，并可先导出 |
| 一个区域 ID 只保存一条城市足迹 | 旅行已是其子记录；城市足迹本身仍唯一 | 照片和分享以城市区域加旅行 ID 引用 |

## 隐私与安全

足迹包含个人位置、日期、备注和照片，属于敏感个人数据。引入后端前需要明确：

- 默认可见性为仅自己，分享需用户主动开启并可随时撤销。
- 用户可以导出全部数据，也可以删除账号并清除所有云端数据、快照和附件。
- 分享页默认不暴露精确日期、备注或照片，除非用户选择公开。
- 传输加密；存储加密或访问控制；访问日志与备份保留期限。
- 上传文件校验类型和大小，不用作任意文件托管；媒体访问必须鉴权或使用有时效的地址。
- 登录会话可在设置中查看和注销；写接口做速率限制。
- 隐私说明和用户协议需要在上线前补齐，涉及的法规要求需另行确认。
