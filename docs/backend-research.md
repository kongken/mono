# 后端功能调研

> 状态：调研与待实现。本文列出的功能均**尚未实现**，不属于当前应用行为。当前已实现的功能见 [功能描述](features.md)，数据约定见 [数据与地图说明](data-and-maps.md)。

## 背景

山海足迹目前是纯浏览器本地应用：足迹保存在浏览器本地存储，通过手动导出、导入 JSON 备份，没有登录、云端同步、分享或附件能力。本文调研如果引入后端，可以额外实现哪些功能，并说明它们对现有规则的影响与建议优先级。

技术选型（自建服务或边缘函数）另行讨论，不在本文范围内。

## 现状与痛点

| 方面 | 当前实现 | 后端可以解决的问题 |
| --- | --- | --- |
| 存储 | 浏览器本地，按网站来源隔离 | 清除站点数据、更换浏览器或设备后记录丢失 |
| 备份 | 手动导出、导入，导入整体替换 | 忘记备份；误导入会覆盖现有记录；没有合并 |
| 足迹模型 | 每个区域 ID 只保存一条足迹 | 无法记录同一城市的多次旅行 |
| 内容 | 颜色、日期、最多 1000 字备注 | 没有照片、附件 |
| 分享 | 无 | 无法给他人查看自己的足迹地图 |
| 区域索引 | 随前端发布，校验依赖 `src/regions.json` | 区划更新后旧备份可能不兼容 |
| 读取失败 | 本地数据校验失败时回落为空，之后可能被自动保存覆盖 | 云同步前必须先处理，避免空数据覆盖云端 |

## 功能清单

### 第一梯队：必须依赖后端的基础能力

#### 1. 账号与云同步

- 用户登录后，足迹和省份独立标记保存到云端，多设备、多浏览器保持一致。
- 登录方式可选邮箱、第三方账号或 passkey，具体方式待定。
- 同步后不再把清除浏览器存储视为数据丢失，手动导入、导出保留为离线备份入口。
- 其他后端功能大多以账号为前提。

#### 2. 本地数据迁移上云

- 首次登录时检测本地已有足迹，并由用户选择：合并、以云端为准、以本地为准。
- 现有导入只支持整体替换，合并规则需要新增：同一区域 ID 冲突时，以日期较新的记录为准，或由用户逐条选择，待定。
- 迁移前提示并提供导出当前数据的入口，保持与现有导入确认流程一致。

#### 3. 云端备份与历史版本

- 每次变更或按时间保留快照，支持回滚到某个版本。
- 用来恢复误导入、误删除或被旧缓存覆盖的数据。

### 第二梯队：显著增加产品价值

#### 4. 照片与附件

- 每条足迹或每次旅行可以关联照片。
- 需要文件存储、大小和数量限制、缩略图生成，以及访问权限控制。
- 可选：读取照片拍摄地点信息，建议关联到对应城市。读取前需要提示用户，并说明处理方式。

#### 5. 同一城市多次旅行

- 数据拆为“区域”和“旅行”两层：一个城市可有多次旅行，各自有日期、备注和照片。
- 地图着色规则需要重新定义，例如取最近一次旅行的颜色，或按次数深浅显示。
- 统计口径增加“旅行次数”，现有“已留下足迹”仍按城市数量计算。
- 这会改变 [功能描述](features.md) 中“每个区域 ID 只保存一条足迹”的规则，需要同步更新存储结构和迁移路径。

#### 6. 公开分享页与分享海报

- 生成只读链接，展示省份探索度和足迹地图。
- 隐私级别：仅自己、仅持有链接的人、公开。
- 可选择隐藏备注、具体日期或照片。
- 服务端生成社交预览图，用于链接分享。

#### 7. 共同旅行与好友

- 邀请同行者共同记录同一次旅行。
- 好友之间互看或对比地图，例如“谁去过的省份更多”。
- 需要邀请、确认、退出和权限管理，适合情侣、家人和朋友。

### 第三梯队：体验增强

#### 8. 统计、年度报告与成就

- 年度旅行回顾，例如当年新增城市数量、跨越省份。
- 打卡成就，例如“集齐某省全部城市”。
- 可由服务端定时汇总，用于年度推送或分享页展示。

#### 9. 搜索增强

- 拼音搜索、模糊纠错、跨备注全文检索。
- 其中拼音和模糊纠错也可以在前端实现，不一定需要后端；备注全文检索在记录量大时才有后端价值。

#### 10. 行政区划数据服务

- 前端通过版本号读取区划映射，服务端维护区划更新和旧 ID 的映射。
- 区划变更后，由服务端迁移旧足迹，缓解“区域索引更新可能影响旧备份兼容性”的问题。
- 地图 GeoJSON 仍可随项目静态分发，不需要运行时请求第三方。

#### 11. 路线规划与行程

- 把多个城市连成一次行程，在地图上绘制路线。
- 如需自动估算路程、交通或时间，需要接入第三方地图服务，这与“运行时无需第三方地图请求或 API Key”的约定冲突。接入前需要先决定是否放宽，或仅在后端调用。

#### 12. 提醒与通知

- 例如“一年前的今天你在杭州”的回忆提醒。
- 需要邮件或 Web Push 通道，以及用户可以随时关闭的设置。

## 对现有约定的影响

| 现有约定 | 影响 | 建议 |
| --- | --- | --- |
| 区域 ID 一致，台湾使用 `tw-` 前缀 | 可直接作为后端存储的区域标识 | 保持不变，作为外键或索引 |
| 省份独立标记与城市足迹分别存储 | 云端需保持同样的分离 | 同步时分别处理，删除一类不影响另一类 |
| 统计中已探索省份取两者并集 | 服务端统计需沿用同一口径 | 前后端使用同一份计算逻辑，避免不一致 |
| 存储结构版本为 `1` | 同步和多次旅行会改变结构 | 升级版本号，提供迁移，不把旧数据当作空数据覆盖 |
| 地图随项目分发，运行时无第三方请求 | 后端不改变地图来源 | 保持静态分发 |
| 导入前提供确认和导出入口 | 迁移上云时需要保持同样的保护 | 合并和覆盖前都提示，并可先导出 |

## 隐私与安全

足迹包含个人位置、日期、备注和照片，属于敏感个人数据。引入后端前需要明确：

- 默认可见性为仅自己，分享需用户主动开启并可随时撤销。
- 用户可以导出全部数据，也可以删除账号并清除所有云端数据和附件。
- 分享页不暴露精确日期、备注或照片，除非用户选择公开。
- 存储和传输加密、访问日志、备份数据的保留期限。
- 上传文件的类型与大小校验，避免被用作任意文件托管。

## 同步设计要点

- **离线优先。** 保留本地缓存，联网后同步，不让每次操作都依赖网络。
- **冲突处理。** 初期可采用整体版本号加“最后写入者优先”，后续再按区域记录粒度合并。
- **防止空数据覆盖。** 本地读取失败时不得把空数据同步到云端，也不得覆盖本地原缓存；需要先修复现有“校验失败回落为空”的行为。
- **幂等与重试。** 网络中断后可重试，重复提交不产生重复足迹。

## 建议优先级

| 顺序 | 内容 | 理由 |
| --- | --- | --- |
| 0 | 修复本地读取失败回落为空并覆盖的问题 | 同步前必须先解决，否则可能丢失数据 |
| 1 | 账号、云同步与本地数据迁移 | 解决最大痛点，也是其他功能的前提 |
| 2 | 同一城市多次旅行的数据模型 | 越晚改，迁移成本越高，应在照片和分享前确定 |
| 3 | 照片与附件 | 显著增强旅行记忆 |
| 4 | 只读分享页与海报 | 带来传播，依赖账号与隐私设置 |
| 5 | 年度报告、成就、共同旅行与提醒 | 增强留存，可按需选做 |

## 待决问题

- 登录方式：邮箱、第三方账号，还是 passkey？
- 主要用户所在地区，以及对访问速度、合规的要求。
- 是长期自运营，还是做成可自托管的开源项目？
- 多次旅行的地图着色规则：取最近一次、最多次数，还是按次数深浅？
- 是否需要放宽“运行时无需第三方请求”的约定，以支持路线规划？
- 分享页的默认隐私级别和可公开的字段范围。
