# 后端功能调研

> 状态：调研与待实现。本文列出的功能、数据模型和接口均为**草案**，尚未实现，不属于当前应用行为。当前已实现的功能见 [功能描述](features.md)，数据约定见 [数据与地图说明](data-and-maps.md)。

后端技术选型与基础设施初始化已完成，见 [后端初始化](backend.md)；以下业务功能仍为待实现草案。

## 目的与范围

山海足迹目前是纯浏览器本地应用：足迹保存在浏览器本地存储，通过手动导出、导入 JSON 备份，没有登录、云端同步、分享或附件能力。

本文用于后续后端开发，包含：

- 引入后端后可以实现哪些功能，以及各自的规则、依赖和验收场景。
- 数据模型、接口、同步和迁移的草案。
- 对现有约定的影响、隐私要求、技术选型倾向、分阶段交付和待决问题。

草案中的字段名、路径和规则不是最终约定。实现某项功能时，应在 [功能描述](features.md) 增加对应规则和验收场景；涉及数据字段、版本或备份校验时，同步更新 [数据与地图说明](data-and-maps.md)，并把本文对应条目改为“已实现”或删除。

## 现状与痛点

| 方面 | 当前实现 | 后端可以解决的问题 |
| --- | --- | --- |
| 存储 | 浏览器本地，按网站来源隔离 | 清除站点数据、更换浏览器或设备后记录丢失 |
| 备份 | 手动导出、导入，导入整体替换 | 忘记备份；误导入会覆盖现有记录；没有合并 |
| 足迹模型 | 每个区域 ID 只保存一条足迹 | 无法记录同一城市的多次旅行 |
| 内容 | 颜色、日期、最多 1000 字备注 | 没有照片、附件 |
| 分享 | 无 | 无法给他人查看自己的足迹地图 |
| 区域索引 | 随前端发布，校验依赖 `src/regions.json` | 区划更新后旧备份可能不兼容 |
| 读取失败 | 本地数据校验失败时回落为空，之后可能被自动保存覆盖 | 云同步前必须先处理，避免空数据覆盖云端 |

## 功能详述

### F0 修复本地读取失败覆盖原数据（前置）

- **问题。** 启动时读取本地 JSON 失败或校验失败会回落为空数据，随后的自动保存可能覆盖原缓存。同步后还可能把空数据推到云端。
- **规则草案。**
  - 读取失败时保留原始字符串，不自动写入。
  - 页面提示数据异常，提供导出原始数据和“以空数据开始”的选择；用户确认前不覆盖。
  - 校验失败时尽量保留可识别的记录，并说明丢弃了什么。
- **验收。** 手动把本地存储改坏，刷新后原始内容仍在，页面提示异常且不自动清空；用户选择导出后可拿到原始内容。

### F1 账号与云同步

**目标。** 登录后，城市足迹和省份独立标记保存到云端，多设备、多浏览器保持一致。

**规则草案。**

- 未登录时保持现有本地模式，行为不变；登录是可选的。
- 登录方式待定（邮箱、第三方账号或 passkey）。
- 登录后本地存储作为离线缓存，联网时同步；手动导出、导入保留为离线备份。
- 同步沿用现有区域 ID、颜色、日期和备注校验规则；服务端必须重新校验，不信任客户端。
- 页面选中的省份、搜索和缩放仍不持久化。

**后端能力。** 账号与会话、足迹读写、增量同步、校验、速率限制。

**验收场景。**

1. 在设备 A 登录并记录杭州，设备 B 登录同一账号后能看到杭州及颜色、日期和备注。
2. 离线记录一条足迹，联网后自动同步，不产生重复记录。
3. 两台设备分别修改同一城市，恢复联网后按冲突规则得到确定结果，且不丢失其他城市。
4. 登出后本地缓存的处理方式明确（保留或清除），并有提示。
5. 服务端拒绝非法颜色、不存在的区域 ID、超长备注。

### F2 本地数据迁移上云

**目标。** 首次登录时处理本地已有足迹，避免丢失，也避免意外覆盖云端。

**规则草案。**

- 本地有数据且云端为空：提示后上传。
- 本地与云端都有数据：让用户选择“合并”、“以云端为准”或“以本地为准”。
- 合并规则：同一区域 ID 冲突时，以日期较新的记录为准；日期相同或为空时，以更新时间较新的记录为准；也可改为逐条选择，待定。
- 省份独立标记取并集；同一省份颜色冲突时，以云端为准或让用户选择，待定。
- 执行前显示将新增、更新、覆盖的数量，并提供导出当前数据的入口，与现有导入确认流程保持一致。
- 迁移失败不得清空本地或云端数据。

**验收场景。**

1. 本地有 3 条、云端为空：确认后云端有 3 条，本地保留。
2. 本地与云端有 1 个相同城市、不同颜色：合并后记录数量不重复，且按规则得到结果。
3. 迁移中途断网，重试后结果正确，没有半成品。
4. 取消迁移，本地和云端都不变。

### F3 云端备份与历史版本

**目标。** 误导入、误删除或被旧缓存覆盖时，可以恢复。

**规则草案。**

- 保存快照的时机：每次迁移或导入前，加上定时快照；保留数量或期限待定。
- 用户可以查看快照时间与记录数量，并选择恢复；恢复前自动再保存一份当前快照。
- 快照不可修改，账号删除时一并清除。

**验收场景。** 删除多条足迹后，从历史版本恢复，记录数量与快照时一致；恢复前有确认，且恢复动作本身可撤销。

### F4 照片与附件

**目标。** 足迹或旅行可以关联照片。

**规则草案。**

- 限制类型（例如 JPEG、PNG、HEIC、WebP）、单文件大小和每条足迹的数量，具体数值待定。
- 上传由客户端直传存储，后端签发有时效的上传地址并登记元数据；读取使用有时效的访问地址或经鉴权的代理。
- 生成缩略图用于列表和地图卡片。
- 可选：读取 EXIF 拍摄地点建议所属城市，必须经用户确认后才写入；上传时默认剥离分享可见版本中的位置信息。
- 删除足迹或旅行时，关联照片按用户选择删除或保留。

**验收场景。** 上传照片后在足迹卡片看到缩略图；超限、非法类型被拒绝；删除后文件不再可访问；分享页默认不暴露照片，除非用户开启。

### F5 同一城市多次旅行

**目标。** 一个城市可以有多次旅行，每次有自己的日期、备注和照片。

**规则草案。**

- 城市足迹保留“区域 + 颜色”，旅行为其子记录（日期、备注、照片）。
- 现有记录迁移时，把原有日期和备注转成该城市的第一次旅行；空日期、空备注仍保留为一次旅行，避免丢失。
- 地图着色仍按城市足迹颜色，不随次数变化；是否增加按次数的深浅显示待定。
- 统计新增“旅行次数”；“已留下足迹”仍按城市数量，口径不变。
- 最近足迹和足迹列表的排序规则（按城市最近一次旅行日期，还是展开为每次旅行）待定。

**影响。** 改变 [功能描述](features.md) 中“每个区域 ID 只保存一条足迹”的规则，需要升级存储结构版本与备份格式，并为旧备份提供迁移。

**验收场景。** 同一城市添加两次不同日期的旅行，记录数量（城市）不变、旅行次数为 2；导入旧版本备份后，每个城市有一次旅行；删除其中一次旅行不删除城市足迹，删除最后一次旅行的行为待定。

### F6 公开分享页与分享海报

**目标。** 生成只读链接，展示省份探索度和足迹地图。

**规则草案。**

- 可见性：仅自己（默认）、持有链接的人、公开。
- 分享页可选展示的字段：地图着色、统计、城市名称、日期、备注、照片；默认只展示地图和统计。
- 链接可随时撤销，撤销后立即失效；链接不可被猜测。
- 服务端生成社交预览图，链接分享到社交平台时显示地图缩略。
- 分享页只读，不暴露账号标识。

**验收场景。** 开启分享后用无痕窗口访问可看到地图；关闭后返回不存在；备注和日期默认不出现；预览图能正确显示省份着色。

### F7 共同旅行与好友

**目标。** 邀请同行者共同记录同一次旅行，好友之间互看地图。

**规则草案。**

- 好友需双方确认；可随时解除，解除后互相不可见。
- 共同旅行有创建者和成员；成员可以编辑同一次旅行的日期、备注和照片，权限范围待定。
- 退出共同旅行不删除自己已有的城市足迹。
- 好友对比只展示双方各自选择公开的内容。

**验收场景。** A 邀请 B，B 接受后双方在各自地图看到同一次旅行；B 退出后 A 的记录保留；解除好友后无法再查看对方地图。

### F8 统计、年度报告与成就

- 年度回顾：当年新增城市数量、跨越省份、最长旅行记录。年度口径沿用现有统计口径，旅行次数依赖 F5。
- 成就：例如集齐某省全部城市，规则需在文档中逐条列出，避免与统计口径不一致。
- 服务端可定时汇总并缓存；成就和报告按用户本地时区计算日期。
- 前端也能基于已有数据计算，后端的价值在于推送与分享页展示。

### F9 搜索增强

- 拼音、首字母和模糊纠错可在前端基于 `src/regions.json` 实现，不需要后端。
- 备注全文检索仅在记录量大或跨设备查询时才有后端价值，优先级低。

### F10 行政区划数据服务

- 前端通过版本号读取区划映射；服务端维护区划更新以及旧 ID 到新 ID 的映射。
- 区划变更后，服务端迁移旧足迹，缓解“区域索引更新可能影响旧备份兼容性”。
- 地图 GeoJSON 仍随项目静态分发，不改变“运行时无需第三方地图请求”的约定。
- 与 F1 的服务端校验共用同一份区域索引，避免前后端不一致。

### F11 路线规划与行程

- 把多个城市连成一次行程，在地图上绘制路线。
- 仅按已有城市中心点连线，不需要第三方服务；若要估算路程、交通时间，则需要第三方地图服务，与“运行时无需第三方地图请求或 API Key”冲突。如要引入，应由后端调用并缓存，且先决定是否放宽该约定。

### F12 提醒与通知

- 例如“一年前的今天你在杭州”的回忆提醒。
- 需要邮件或 Web Push 通道；用户可以逐类开关并随时退订。
- 通知内容不得包含超出用户设置的敏感信息。

## 数据模型草案

字段为设计示意，名称与类型可调整。区域标识沿用现有区域 ID 字符串，台湾补充区域使用 `tw-` 前缀。

### 第一阶段（F1–F3）

| 表 | 字段 | 说明 |
| --- | --- | --- |
| `users` | `id`、`created_at`、`deleted_at` | 账号 |
| `identities` | `user_id`、`provider`、`subject`、`email` | 登录身份，一个账号可绑定多个 |
| `sessions` | `id`、`user_id`、`expires_at`、`device` | 会话，可在设置中查看和注销 |
| `footprints` | `user_id`、`code`、`name`、`province`、`color`、`date`、`note`、`updated_at`、`deleted_at` | 城市足迹；`(user_id, code)` 唯一；`deleted_at` 用于同步删除 |
| `province_marks` | `user_id`、`province`、`color`、`updated_at`、`deleted_at` | 省份独立标记，与城市足迹分别存储 |
| `sync_state` | `user_id`、`revision`、`updated_at` | 用户级单调递增版本号，每次变更加一 |
| `snapshots` | `id`、`user_id`、`reason`、`created_at`、`visit_count`、`payload` | 备份快照，`reason` 例如迁移前、导入前、定时 |

规则：

- `footprints` 与 `province_marks` 分开，保持“移除一类记录时保留另一类记录”。
- 已探索省份仍由两者并集计算，服务端和前端使用同一份逻辑。
- 服务端校验沿用现有备份校验：颜色白名单、日期格式、备注不超过 1000 字符、城市与所属省份及名称与区域索引一致。

### 存储结构版本

- 本地与导出备份当前为 `version: 1`。
- 引入 F5 后升级到 `version: 2`，增加旅行层；导入时必须同时接受 1 和 2，旧版本自动迁移，不把旧数据当作空数据覆盖。
- 云端 schema 变更使用独立的迁移脚本，与前端存储版本分别管理。

## 接口草案

仅表示形态，具体路径和返回值实现时再定。所有写接口服务端重新校验；所有读写限定当前用户。

### 第一阶段

| 接口 | 作用 |
| --- | --- |
| 登录、登出、会话查询 | 账号入口 |
| `GET /api/footprints` | 返回完整数据和当前 `revision`，结构与现有备份一致 |
| `GET /api/footprints?since=<revision>` | 增量，返回变更和已删除项 |
| `PUT /api/visits/:code`、`DELETE /api/visits/:code` | 保存、删除城市足迹 |
| `PUT /api/provinces/:id`、`DELETE /api/provinces/:id` | 保存、取消省份独立标记 |
| `POST /api/sync` | 批量提交离线期间的变更，请求带 `base_revision`，返回新 `revision` 与冲突 |
| `POST /api/migrate` | 本地数据迁移，参数含策略（合并、云端为准、本地为准），支持预览 |
| `GET /api/export` | 导出完整数据，格式与现有备份一致 |
| `GET /api/snapshots`、`POST /api/snapshots/:id/restore` | 列出、恢复快照 |
| `DELETE /api/me` | 删除账号及全部数据 |

## 同步设计草案

- **离线优先。** 本地缓存始终是读写入口，联网后后台同步。
- **版本号。** 服务端每个用户一个单调递增 `revision`；客户端记录已同步的 `revision`。
- **冲突。** 初期按记录粒度，以更新时间较新者为准，删除使用 `deleted_at` 标记并参与比较；后续可改为字段级合并。冲突结果在接口中返回，前端可提示用户。
- **幂等。** 同一变更重复提交不产生重复记录，可使用客户端生成的变更 ID。
- **防止空数据覆盖。** 客户端在本地读取失败（见 F0）时不得向云端推送；服务端对“批量清空”类请求要求显式确认，并先保存快照。
- **时间与时区。** 旅行日期是字符串日期，不随时区转换；`updated_at` 使用 UTC。

## 对现有约定的影响

| 现有约定 | 影响 | 建议 |
| --- | --- | --- |
| 区域 ID 一致，台湾使用 `tw-` 前缀 | 可直接作为后端区域标识 | 保持不变，作为外键或索引 |
| 省份独立标记与城市足迹分别存储 | 云端需保持同样的分离 | 同步时分别处理，删除一类不影响另一类 |
| 统计中已探索省份取两者并集 | 服务端统计需沿用同一口径 | 前后端共用同一份计算逻辑 |
| 存储结构版本为 `1` | F5 和同步会改变结构 | 升级版本号，提供迁移，不把旧数据当作空数据覆盖 |
| 地图随项目分发，运行时无第三方请求 | 后端不改变地图来源 | 保持静态分发；F11 外部服务需单独决定 |
| 导入前提供确认和导出入口 | 迁移上云时需要保持同样的保护 | 合并、覆盖、恢复前都提示，并可先导出 |
| 一个区域 ID 只保存一条足迹 | F5 会改变 | 先定数据模型再做照片和分享 |

## 隐私与安全

足迹包含个人位置、日期、备注和照片，属于敏感个人数据。引入后端前需要明确：

- 默认可见性为仅自己，分享需用户主动开启并可随时撤销。
- 用户可以导出全部数据，也可以删除账号并清除所有云端数据、快照和附件。
- 分享页默认不暴露精确日期、备注或照片，除非用户选择公开。
- 传输加密；存储加密或访问控制；访问日志与备份保留期限。
- 上传文件校验类型和大小，不用作任意文件托管；媒体访问必须鉴权或使用有时效的地址。
- 登录会话可在设置中查看和注销；写接口做速率限制。
- 隐私说明和用户协议需要在上线前补齐，涉及的法规要求需另行确认。

## 技术选型（已确定）

采用与 `neo-box` 一致的 Go + Butterfly + Gin + ConnectRPC + Ent；数据库为 PostgreSQL，辅助存储为 Redis，对象内容使用 S3。前端保留 React + Vite + shadcn，增加生成的 Connect-Web 客户端。

后端服务、依赖接入、Ent schema、健康接口和开发环境已初始化，详见 [后端初始化](backend.md)。F0–F12 的业务功能仍待实现，本文接口和业务模型草案尚不是线上约定。

## 待决问题

- 登录方式：邮箱、第三方账号，还是 passkey？
- 部署方式与运行环境：Go 服务如何托管、数据库和 S3 供应方如何配置？

- F5：地图着色是否按次数深浅；最近足迹的排序是否展开为每次旅行；删除最后一次旅行是否同时删除城市足迹。
- 照片限制：类型、大小、数量，是否读取 EXIF 位置。
- 分享页默认可公开的字段范围。
- 是否放宽“运行时无需第三方请求”的约定以支持路线规划。
- 是否需要邮件或 Web Push 通道。
