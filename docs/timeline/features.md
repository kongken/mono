## Timeline 文字记录

Timeline 记录属于当前 OzID 账号，浏览器通过 BFF 的 `bff.timeline.v1.TimelineService` 访问。服务端从内部会话凭证取得用户身份，客户端不能提交用户 ID。

记录需要标题、日期和 IANA 时区，可选发生时间、分类、地点、备注、金额/三位大写币种和网页书签。日期与时间由服务端解析和排序；金额使用最小货币单位整数保存。网页书签只保存经过 scheme、控制字符、长度和内网目标校验的用户输入，不会请求目标 URL。

列表支持搜索、分类和日期范围组合筛选，并按发生时间倒序、ID 升序稳定排序。删除先进入回收站，恢复后回到原排序位置；永久删除需要明确调用 purge。更新和删除可携带 expected revision，版本不匹配返回冲突；创建携带 mutation id 时重放返回原记录。

账号注销会删除 Timeline 记录，并把关联对象的 opaque key 放入不含用户 ID 的清理队列。清理队列可安全重试。BFF 未配置 Timeline upstream 时不会挂载入口。

## 浏览器页面

`apps/timeline`（`@kongken/timeline`）按 Stitch 设计稿（项目 `11000415110204392416`，屏“Timeline 时间线与记一笔抽屉 - 桌面端”）实现这一屏：220px 左侧栏（时间线、回收站可切换；分类管理、设置与 MCP 按设计稿显示但置灰，因为分类由记录自身产生、MCP 端点是机器协议，都还没有对应的服务端页面）、底部账号卡片（昵称、同步状态、退出登录或去 OzID 登录）、顶部“检索手账”与“写手账”、页头“<年份> 年 阳历记录本”与“记一笔”、筛选条（分类、日期范围、生效中的筛选标签与“清除筛选”）、按月份分节再按日分节的时间线（今天的日期带“今天”标记）、每条记录的金额、分类、地点、备注与书签，以及分页的“加载更多记录”。

“记一笔”是右侧抽屉，字段与记录接口一致：标题（必填）、日期（必填）、时间（可留空）、IANA 时区（默认取浏览器时区，可在常用时区里改）、分类、地点、金额与币种、备注。校验规则与 `internal/timeline/application` 一致，在提交前就地拦下；写入携带 mutation id，重复点击不会写两次。

附件（KON-106）走 `bff.timeline.v1.MediaService`，与服务端同一套规则：JPEG / PNG / WebP / PDF，单个不超过 10 MiB，一条记录最多 20 个。保存时先写记录，再对每个文件 `PrepareUpload`（服务端预留对象并签名）→ 浏览器直接 `PUT` 到对象存储（只发送服务端签名覆盖的 `Content-Type` 等头，不带 Cookie）→ `CompleteUpload`（服务端核对大小与文件真实类型后置为 ready）。某个文件失败时记录已经保存，抽屉给出失败原因与“重试上传”：重试只对失败的附件重新签名上传，不会再写一条记录。记录卡片上的附件通过 `ReadMedia` 带会话读取，图片就地预览，PDF 交给浏览器下载，对象存储保持私有；删除走 `DeleteMedia`（mutation id + `expected_revision`，当前附件不可变，revision 恒为 1），存储空间由后台清理过程回收。

页面只调用 BFF 的 `bff.timeline.v1.TimelineService`，Cookie 随请求发送，账号页面都在 OzID；构建必须给出绝对的 `VITE_API_BASE_URL` 与 `VITE_OZID_ORIGIN`，缺失即构建失败。读取失败显示错误与“重试”，不把空列表伪装成“还没有记录”。

测试：纯规则（分组、日期与时区文案、金额换算、草稿校验、附件规则）由 `node --test` 覆盖；`tests/` 的 Playwright 用例用模拟 BFF 与模拟对象存储跑设计稿的版式与交互（侧栏与导航、月/日分节、搜索与筛选、抽屉的必填校验与一次写入、回收站恢复、读取失败重试、附件签名上传与完成、上传失败后的局部重试、过期链接重试、私有读取预览与删除），在 CI 的 frontend 任务里执行。

当前限制：附件在写记录的同一个动作里上传，超大文件还没有分片或断点续传；分类筛选的选项来自已加载的记录，服务端还没有分类目录过程。
